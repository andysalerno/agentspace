## Features

*These are large feature-work changes that are scheduled.*

- [ ] FEAT: VS Code service should not actually spawn in the container until a user requests it explicitly by clicking "open in VS Code" (or similar). This should reduce idle memory usage for the common case where VS Code is never launched.
- [ ] FEAT: CLI View. Similar to "Agents" view but launches directly to a terminal instance (in-browser) instead of our custom chat UI.
- [ ] FEAT: 'inspect' mode for the conversation: a sidebar on the right (well, UX can be determined) that exposes as much information as we can about the session; anything that can be captured either from the json stream (if enabled) or from the OTEL, or whatever is the most fine-grained source of info. We should be able to visually drill down into every message and see tool calls, cache usage, token usage, etc. Progressive disclosure - we can keep drilling further and further and exposing more and more info via the UI. Ideally this would be handled by the same mechanism in both CLI View and Chat view, though perhaps the details of those modes (ACP for chat view, and direct CLI invocation for CLI view) will result in different capturing requirements (but hopefully at least the same display logic).
- [ ] FEAT: "app" or "service" support. It would work like this: when chatting with an agent (via any UI or via CLI mode) the user can ask for an app or service, e.x. "Give me a webapp that lets me track my dog's eating schedule." Today, there's some skill that tells the agent how to host an app within a container - because we, by design, have a hardcoded port we expose in the agent containers that allows it to host a service alongside its own session. This feature would be similar, but not exactly the same: when the user asks "give me a webapp that lets me track my dog's eating schedule," there will be a skill that tells the agent it can create new apps and service by invoking the cli tool "agentspace app", similar to the existing "agentspace memory" and "agentspace skills". The CLI shape is up to you, but imagine the agent invokes "agentspace app new --name DogFoodTracker". This provisions a new "app", which is a new concept in the agentspace service that you must add. What is an "app"? Well, it's similar to a "workspace", perhaps even powered by the exact same implementation - but besides being a persisted "at rest" data store, it also defines how it may be 1. tested, 2. compiled, and 3. run (possibly on an exposed port). E.x. an app might specify its "test" command is "dotnet test dogfood.csproj", or maybe "cargo test", or maybe "run-arbitrary-test.sh". Same idea with build and run. When an agent is done constructing the app, the user can view the app (its workspace, its test/build/run commands, which agent created it, etc) in a new view called "apps" (alongside existing views like "memory" etc).
